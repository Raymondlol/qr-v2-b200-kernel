# Dead ends — DO NOT re-explore these (each was tested or rigorously evaluated)

## Precision below tf32x3 — MANTISSA wall was a TF32-SOLVE artifact; fp16x3 now SHIPPED, fp8/fp4 SPEED-dead (CORRECTED + MEASURED 2026-06-26, branch `fp8-fp4-attack`)
**The old "1×TF32 fails / no room below tf32x3 / fp8 DEAD / fp16x3 ~wash" claims were WRONG and are overturned.** See `docs/FP8_SESSION_PROGRESS.md` + memory `qr-v2-solve-tf32-floor-artifact`. The mixed@640 ~1.9× margin that looked like a trailing-GEMM floor was caused ENTIRELY by `torch.linalg.solve_triangular` running in tf32 (`allow_tf32=True` is global, so cuBLAS trsm honors it). Attribution on the REAL custom_kernel (`experiments/microbench_attrib.py`, 3 seeds): real (tf32 solve) margin **1.82×**; `allow_tf32=False` everywhere **797×**; tf32 ON but ONLY solve→fp32 **797×** (IDENTICAL → the solve is the SOLE culprit at n≤512); solve→fp64 **833×**. So at n≤512 the trailing GEMM was NEVER the binding constraint — tf32x3/fp16x3 there have ~800× precision headroom that was masked by the tf32 solve. (n≥1024 uses 1×TF32 trailing, so solve→fp32 only lifts n1024-mixed 1.96×→2.09×.) The solve-fix lives in `experiments/cand_fp16x3_solvefix.py` (+2.4% geomean AND margin 800×, 22/22).
- **fp16x3: OFFICIAL WASH — tried & REVERTED (still a dead end on official HW).** Fused FP16x3 trailing/gram (3-term hi/lo fp16 split, fp32 accumulate) = same ~22-bit accuracy as tf32x3 (relerr 9.2e-7). Modal lab measured +3.6% (570 vs 876µs isolated fat shape) — **but OFFICIAL submissionV6 = 5997µs ≈ V5 tf32x3 5915 = WASH (the +3.6% did NOT transfer)** → `submission.py` reverted to V5 tf32x3. ROOT CAUSE: fp16x3 uses **fp32-accumulate**, and B200 fp16-fp32acc = 482 TFLOP/s = exactly the tf32 rate (the "fp16 TC = 2× tf32" framing is WRONG for fp32-acc — the 2× is fp16-ACC peak only, too lossy for the trailing). No physical advantage; the Modal gain was a Triton-codegen artifact (explicit-fp16 vs `input_precision="tf32x3"` emulation). `experiments/cand_fp16x3.py` kept as the artifact; commit f981cce / tag `fp16x3-win` predates this finding. See docs/FP8_SESSION_PROGRESS.md banner + [[qr-v2-testing-setup]].
- **fp8 (e4m3, 3-bit mantissa): ACCURACY-viable, SPEED-DEAD (now rigorously MEASURED, not a workflow verdict).** Overturns the old "mantissa wall": fp8 e4m3 6-dot Ozaki (k3/k3/T2) on the real pipeline = mixed@640 margin **10.8× SAFE** (10-dot = 352×) — fp8 CAN hit the gate. But it is not a speed win: a fully-fused autotuned fp8-Ozaki-6dot kernel = 941µs vs fused tf32x3 1091µs (only 14% faster); add the Ozaki per-tensor amax scale cost and the realistic version is **3.7× SLOWER (4087µs)**. `experiments/microbench_fp8_{speed,fused}.py`. Dedicated cores VERIFIED used (`experiments/microbench_fp8_coreverify.py`): PTX of `tl.dot(fp8)` emits `tcgen05.mma` (Blackwell 5th-gen tensor core, not a SW upcast); `torch._scaled_mm` (cuBLAS fp8) hits 1896 TFLOPs = 100% of fp8 peak at 4096³ but only **2 TFLOPs = 0% of fp8 peak on our 512×128×384 trailing shape**. The K-poor batched trailing SHAPE is the wall, not the API/core. fp8's two-layer loss (needs 2× the dots AND per-dot ≤1.13× tf32 even when K-rich, `experiments/microbench_feed_gemm.py`) leaves fp8-6dot ~2–2.4× slower than tf32x3.
- **mxfp8 / nvfp4 / mxfp4 block-scaled: DEAD here.** `tl.dot_scaled` block-scaled tcgen05 mxfp8 = **1.16–1.29× SLOWER** than plain fp8 `tl.dot` on the real shapes (`experiments/microbench_mxfp8_vs_fp8.py`) — the HW "block scaling is free" result applies to LARGE shapes only; on small K-poor shapes the scale loading adds overhead. fp4 = fp8 throughput on dense B200 (NOT 8×; that's marketing/sparse/GB300) + needs MORE Ozaki dots → strictly worse than fp8.
- **1×TF32: +7.1% geomean BUT reseed-DQ.** mixed@640 worst-of-640 sfr reaches **19.7 across 12 seeds (margin 1.02, gate 20)** = reseed-DQ near-certain. NOT viable. `experiments/microbench_1x_reseed.py`.
- **2-term TF32 (split one operand): TESTED, useless.** No speedup (split traffic is the cost, not matmul count) AND worse accuracy (n=512 mixed scaled 44). `experiments/cand_R_2term512.py`.
- **lowprec-panel (run the panel reductions in tf32/fp16): DEAD.** The `_panel_kernel` has NO `tl.dot` — it's pure `tl.sum` reductions + elementwise FMA = CUDA-core/SRAM-bandwidth bound. B200 low-precision speedups apply ONLY to tensor cores → ~0 ALU gain, AND it corrupts the reflectors (tf32 τ → ‖QᵀQ−I‖ ~0.5 vs gate 0.012). (workflow verdict, high confidence)

## Large-n custom path
- **Custom two-level for n=4096 (small ib so SRAM fits): DEAD (cand_U).** n=2048 687ms, n=4096 1228ms — 9-22× WORSE than geqrf. batch=2-8 → only 2-8 one-program-per-matrix CTAs on 148 SMs = catastrophic occupancy. `experiments/cand_U_customLargeN.py`. **NOTE: this was tested with default-4-warp panel; re-tested WITH panel-warps (cand_X) it WINS n=2048 but still loses n=4096.**
- **geqrf-panel (wide block) + TF32 trailing: DEAD (cand_G/N).** ≈ geqrf — a wide cuSOLVER panel on [2048,512] costs ≈ the whole thing; narrow blocks add per-call overhead. `experiments/cand_N_largeN512.py`.
- **Stream-parallel geqrf (one CUDA stream per matrix): ILLEGAL.** Worked great (n=2048 77k→17k) but submission checker rejects any "stream" usage. `experiments/_INVALID_cand_L_streamgeqrf.py`. Same for CUDA graphs.
- **TSQR → flat output: legal but washes.** TSQR's tree reflectors don't fit the flat layout directly, BUT Householder-reconstruction (form Q explicitly O(n³) + LU-without-pivoting of top n×n block → unit-lower Y=v_i, τ from diagonal) recovers valid flat (H,τ). It ~3×'s the per-matrix flop and must still beat cuSOLVER on n=2048/4096 → wash. (workflow verdict, high confidence)

## CholeskyQR — torch-primitive version DEAD at every shape; custom-kernel version is bounded + needs 2–3 hand-written kernels (measured 2026-06-25)
**Original claim was over-generalized from n=512 only; now measured across all four floor shapes.** `experiments/microbench_choleskyqr2.py` (B200, shifted CQR2 components, median µs):

| shape | gram | chol | trsm | CQR2 total | geqrf | our path |
|---|---|---|---|---|---|---|
| b=640 n=512 | 719 | 4743 | 5819 | **22345** | 1,070,470 | ~14800 (custom) |
| b=60 n=1024 | 345 | 4089 | 3412 | **15662** | — | ~10900 (custom) |
| b=8 n=2048 | 269 | 8677 | 5640 | **29246** | 76876 | ~35000 (custom) |
| b=2 n=4096 | 444 | **24844** | 3278 | **57354** | 54479 | 52200 (geqrf) |

Key facts this settles:
- **n=512:** CQR2 (22ms) loses to our 14ms Householder. Correctly dead here.
- **n=2048:** CQR2 (29ms) beats geqrf (77ms) but only ~ties our existing custom path (35ms); + reconstruction erases the margin → no net win.
- **n=4096 (the real remaining floor):** CQR2 (57ms) ≈ geqrf (54ms) — does NOT beat it, **before** reconstruction. The killer is `torch.linalg.cholesky` of one 4096² matrix at b=2 = **24.8ms = ~1.8 TFLOP/s = critical-path-bound — the SAME low-occupancy floor as geqrf.** cuSOLVER chol does NOT escape the floor; it just swaps the serial Householder panel for a serial Cholesky panel. **Empirical proof that there is no library shortcut: geqrf, cuSOLVER cholesky, and cuSOLVER trsm/LU all hit the same low-batch-large-n wall.**
- **"dense ⇒ numerically safe" is FALSE** (CPU-verified): `reference.generate_input(case='dense', cond=1)` is heavy-tailed — cond(A) reaches **8.4e6 (n=512) / 8.1e5 (n=2048)**, so cond(G)=cond² ~ 1e11–1e13, and **unshifted fp32 CholeskyQR `_LinAlgError`s at n=2048**. A reseed-safe CholeskyQR needs **fp32 (not tf32x3, not plain-TF32) Gram + Demmel-shifted CQR3** — i.e. MORE passes, not the cheap tf32x3-CQR2 the optimistic flop model assumed. (Plain TF32 Gram is the `_LinAlgError`/nan bug that killed the original `microbench_choleskyqr.py` large-n rows.)
- **Reconstruction trap:** the only drop-in-CORRECT Q→flat(H,τ) is `geqrf(Q)`+sign-fix — but that is the SAME geqrf primitive, so it re-imports the floor (~52ms at n=4096). A cheap reconstruction (Ballard–Demmel/LAPACK ORHR_COL = unpivoted GETRFNP, ~n³/3) needs a CUSTOM batched GEMM-trailing LU kernel (torch.linalg.lu is pivoted → breaks the no-pivot stability guarantee AND is cuSOLVER-bound).

**UPDATE 2026-06-26 — CholeskyQR floor-breaker NOW MEASURED-DEAD (was "parked"), `experiments/microbench_cqr_floorbreak.py` on B200, `results/cqr_floorbreak_NOGO.txt`:** the full SAFE path (fp32 Gram + Demmel-shifted CQR2 AND CQR3, also tf32x3-Gram-CQR3) **FAILS with `_LinAlgError` at BOTH b=8 n=2048 and b=2 n=4096** on the dense/ill-conditioned seeds — the Demmel shift `s=11*n*eps*max_diag(G)` is INSUFFICIENT at cond(G)~6.5e11, so `torch.linalg.cholesky` raises and the path produces NO valid factorization (let alone beats geqrf; reconstruction never reached). A larger shift would destroy accuracy. **So the floor-breaker can't even FACTOR the real inputs → fully dead, not just bounded.** This closes the last non-overlap direction surveyed 2026-06-26 (5-agent survey: CholeskyQR/floor-breaker, GEQRT3-recursive-WY panel, in-block-TSQR panel, solve/precision revive, leader-gap — ALL drop/dead). The deployable+research optimization space is measured-exhausted; ship V5 tf32x3 5915µs.

**Verdict:** torch-primitive CholeskyQR is dead everywhere. A custom CholeskyQR floor-breaker (custom blocked tensor-core Cholesky + custom unpivoted-GETRFNP reconstruction) is *possible* but **bounded + lower EV than the engine**: it targets only n=4096 b=2 (n=2048 already won by our custom path), and needs **2–3 hand-written tensor-core factorization kernels**, MORE engineering surface than the single warp-specialized trailing-GEMM engine, for a single-case payoff.
- **Floor-probe result (`experiments/microbench_floor_and_engine.py`, B200 2026-06-25): a right-looking BLOCKED Cholesky (trailing = GEMM) already BEATS monolithic cuSOLVER `cholesky` — n=2048 b=8 1.33×, n=4096 b=2 2.86×** (cuSOLVER 25.5ms → blocked 8.9ms; Rinv+A@Rinv apply = 3.8ms+0.3ms). So the floor-breaker is NOT fully dead and there is large headroom below cuSOLVER. BUT the full path is still ~35ms (CQR3-safe blocked chol + custom unpivoted-LU recon) vs geqrf 52ms = ~1.5× on **one of twelve** cases ≈ ~3% geomean, for 2–3 custom kernels. **Park it:** if a custom tensor-core blocked Cholesky gets built anyway (e.g. as a byproduct of the engine), revisit; otherwise the trailing-GEMM engine is strictly higher EV.

## Tsolve via triangular-inverse + GEMM (cand_tsolve) — DEAD (slower + precision regression)
Engine attack lever 2. Replaced `Y = solve_triangular(Mᵀ, W)` (large RHS = trailing width) with: invert M (small b×b RHS=I) → `Y = Tᵀ@W` GEMM. Hypothesis (from cqr_components: trsm slow, GEMM fast) was WRONG here. Measured (Modal, vs 6907 gram baseline): geomean **7230 (WORSE)**; n=1024 8.8→9.3ms, n=2048 27.3→31.8ms slower. AND precision regressed: n=1024 mixed 2.0×→**1.4×**, n=512 mixed 2.0×→1.8× (the GEMM apply was 1×TF32 vs the original fp32-accurate `solve_triangular`). Two lessons: cuSOLVER batched trsm at small b is **launch/latency-bound, not RHS-width-bound** (shrinking RHS doesn't help), and the T-application needs fp32-class precision. The real Tsolve cost (18–21%) is per-apply launch overhead → only fixable by FEWER/BIGGER applies (= the recursive-blocking lever), not the inverse trick.

## Raw-PTX / load_inline tf32x3 trailing GEMM (the "warp-specialized engine") — BUILT, WORKS, but NOT WORTH IT (2026-06-25)
Attempted the hard engine end-to-end. Toolchain confirmed: `load_inline` compiles + runs on B200 sm_100 (needs a CUDA-**devel** base image — `modal_cuda.py`; the torch cu128 wheel ships the runtime but NOT nvcc), and `mma.sync.aligned.m16n8k8.f32.tf32` assembles. Built a correct double-buffered (cp.async) tf32x3 tiled GEMM (`experiments/cuda_gate{1,2,3}.py`): relerr ~3e-6, **51 TF/s n=1024 / ~45 n=512 = ~1.2× over Triton's tf32x3 (41/38)**. So a hand-written kernel DOES beat Triton. It is still DEAD for three compounding reasons:
1. **Bounded payoff.** The profiler showed the trailing GEMM is only **26% of n=512 / 21% of n=1024**; and n≥1024 already uses faster cuBLAS-1×TF32 (337 TF/s), so a tf32x3 kernel only helps **n=512** (where tf32x3 is precision-required). 1.2× on 26% ≈ **~1.04× on n=512 ≈ ~1.5% geomean.** Even pushing the kernel to its ceiling (~70 TF/s; the K-poor shape caps even cuBLAS at 20-31%, so tf32x3÷3 ≈ 78 is the wall) only gets ~2%.
2. **TLX absent** (`triton_tlx`/`tlx` ModuleNotFoundError on triton 3.6.0) — no Triton-native warp-spec route; persistent/TMA Triton variants were WORSE than the current fused kernel.
3. **DEPLOYMENT BLOCKER:** `load_inline` needs **nvcc on the competition eval machine**, which the standard torch-only environment does NOT have (had to build a cuda-devel image just to compile on Modal). Shipping precompiled PTX/cubin is even more fragile. So raw CUDA likely can't even run in the real submission.
**Conclusion: the gap is NOT closeable via a faster trailing GEMM kernel** (raw-PTX included) — the trailing is too small a share, n≥1024 already fast, the shape caps efficiency, and raw CUDA isn't deployable. The real remaining levers are algorithmic: a faster PANEL (41% of n=512, latency-bound by the sequential reflector dependency), BIGGER-K trailing shapes (lifts the existing deployable kernels toward 50%+), or a different decomposition. See NEXT_STEPS.

## GOTCHA: in-place Triton kernel under @triton.autotune MUST use restore_value
The glue-fusion `_bmm_x3_sub_kernel` does `C -= A@B` in-place. `@triton.autotune` re-runs each config on the SAME buffers to time them, so the autotune call over-subtracted C ~5× → garbage. It PASSED the gpu_bench benchmark (the warmup pass absorbed the autotune corruption into a discarded output) but FAILED `--stress` n=176/n=352 (no warmup → first call IS the autotune → corrupt) with residual 1e9–1e13. This would DQ the real submission (test mode runs each case fresh). Fix: `@triton.autotune(..., restore_value=['C'])` restores C before each trial. Lesson: any read-modify-write Triton kernel needs `restore_value`; and `--stress` (fresh single call per case) catches what the warmed benchmark hides — always gate on it.
